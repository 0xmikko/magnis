## The Goal

1. After first synchronization, Graph contains 100% of the DM, contact and tracked-author post IDs returned by the completed provider walks.
2. After one restart and two identical polls, there are zero duplicate records and zero missing IDs among newly returned messages and tracked posts.
3. When X returns a 429 with reset time T, Accounts remains paused until T and resumes without clearing imported data.

## Why now

Now the X Source fetches only ten recent posts per tracked handle every five minutes, without history pagination, DM import or following import.

The inspected catalog base is `8f1e371`; the inspected app base is `fe2e0174c`.
The reference conversation is Codex session `01a0c40c-b093-7e60-9eb2-9978a058aa18`.

- `sources/x/src/surfaces/x/fetch.ts` ignores provider pagination and returns an incremented numeric cursor.
- `sources/x/src/api.ts` reads profiles and one timeline page; it invents a sixty-second retry delay when provider timing is absent.
- `sources/x/manifest.toml` declares app-only bearer authentication and one `x` surface.
- `modules/x/module/service.ts` ingests profiles and posts, links tracked profiles to contacts, and suppresses identity-link failures.
- `modules/x/module/__tests__/importFollowing.test.ts` confirms the old handle-based following import was deliberately removed.
- `modules/contacts/module/service.ts` already offers idempotent `contacts.create`, keyed by `client_id`.
- The app stores an OAuth credential at connection time but has no runtime path to persist a replacement returned during refresh.
- Its Source runtime returns before calling the provider when tracked handles are empty, which would suppress independent DM and contact imports.
- `acceptance/telegram-performance` already measures Telegram and Google against exact app and catalog revisions outside CI.

The earlier Google delivery uses IMAP for historical Gmail download and REST history for subsequent changes.
The earlier Telegram delivery uses bounded pages, durable continuation and provider-directed holds.
Their recorded live results establish their own behavior, rather than a Twitter speed estimate.

## The target

### Data and provider boundaries

The owner selected following contacts and participants of personal conversations.
Followers are excluded.
Importing a person does not enable Track on X automatically.
Only the existing tracked set authorizes timeline reads.
An empty tracked set disables posts, never account DM or following reads.
The host's empty-tracking shortcut applies only to a certified tracked-identity-only target.

The proposed DM path is the ordinary X API.
Its [lookup documentation](https://docs.x.com/x-api/direct-messages/lookup/introduction) limits accessible events to the preceding thirty days.
[User timelines](https://docs.x.com/x-api/posts/timelines/introduction) expose up to 3,200 recent posts per author.
These are provider limits, not a promise to retrieve every historical item.

Encrypted [X Chat](https://docs.x.com/xchat/introduction) uses a different API and requires client-held decryption keys.
Its inclusion remains an owner decision before the implementation contract.
Ciphertext must never be stored or displayed as a successfully imported plaintext message.

Previously imported history remains available after it leaves the provider's accessible window.
Initial history completion precedes regular catch-up, as in the existing Gmail bootstrap path.
This scope does not promise continuous DM delivery during a quota-limited initial import.
Absence from a limited timeline or DM window is not a deletion.
Unfollowing someone does not delete the contact or imported history.

### Connection and credential lifetime

Use the host's existing OAuth2 PKCE connection flow.
Request only `tweet.read`, `users.read`, `follows.read`, `dm.read` and `offline.access`.
The Source exchanges the code and verifies the immutable account ID through `/2/users/me`.
An app-only token cannot satisfy this connection contract.

Store the token bundle as the existing single minted credential, named `refresh_token`.
The bundle contains the access token, refresh token, explicit expiry and verified account ID.
The host stores its opaque bytes in the existing encrypted credential location.
Provider tokens never enter sync cursors, Graph records, logs or reports.

The Source implements the existing `magnis.auth.step` operation for credential maintenance.
This operation uses the existing credential-and-identity result and does not mutate the sync protocol.
A valid bundle returns unchanged without a provider refresh request.
An expired bundle refreshes once and returns the replacement through the existing credential-and-identity auth result.

The host calls this operation only when the certified OAuth Source declares it callable.
It verifies the unchanged provider identity and persists changed credential bytes before starting a data fetch.
Concurrent calls share one refresh under the existing account lifecycle owner.
The host calls credential maintenance through an acquired binding; the replacement cannot bypass that binding's identity and generation checks.
Disconnect or repair cannot receive an older generation's replacement.

Saving a replacement does not start a new account generation or erase sync progress.
A refresh or persistence failure prevents the data fetch and remains visible.
A crash after provider token rotation but before durable saving can require reconnect; it cannot be represented as successful maintenance.
No previous token is substituted after rejection.
A restart uses the persisted replacement.

The compatibility declaration changes deliberately from app-only authentication to verified OAuth user identity.
The mixed initial walk declares target `full_snapshot`, opaque continuation/checkpoint and coverage `snapshot`; it is no longer a tracked-identity-only target.
Completion covers the accessible API window, not the provider's all-time history.
Existing bearer connections require explicit reconnect.
Keep their Graph history and stable provider anchors; do not silently convert their credentials.

### Historical import and later changes

Retain the `x` surface and the existing Poll worker.
Extend its opaque cursor to carry separate following, DM and per-author timeline continuations.
The cursor records which bounded provider page is next and the last fully committed forward checkpoints.
Initial import walks following and DM pages, then rotates historical timeline pages between tracked authors.
On the terminal page, its candidates become the next poll's committed checkpoints; no checkpoint changes before admission.
It contains IDs and paging state, never message bodies or credentials.

History is read through bootstrap pagination, as Gmail history is today.
No numeric `traversed` ranges are invented for X Snowflake IDs.
Every X account, post and DM ID remains a string.

A Source response performs bounded work and yields to the host.
Start with at most one provider data page per response and one bounded identity lookup when needed.
Keep the current five-minute poll interval until a measured requirement justifies changing it.
Do not add a second scheduler, local database, history store or background runner.

Following uses `/2/users/:id/following` and its real continuation token.
X offers no following change token; later following passes therefore enumerate the list again.
A renamed account remains the same profile because its immutable provider ID is the anchor.

DM history uses `/2/dm_events`, provider pagination and sender/participant expansions.
MessageCreate events become message records.
Membership events may provide participant identities but never inflate the message count.
Required profile lookups are batched; missing required identity data fails the page.

DM catch-up reads newest events until it reaches the committed event boundary, or the provider ends the accessible window.
This endpoint has no `since_id` parameter; do not invent one.
A page containing only older known events advances continuation without duplicating Graph records.
A checkpoint outside the accessible window records an unrecoverable provider gap instead of claiming complete coverage.

Tracked authors use paginated `/2/users/:id/tweets`.
Preserve full text, article bodies, media references and reply/repost classification.
Capture a newest-ID boundary before historical pagination.
Commit the candidate high-water mark only after all pages belonging to that forward walk succeed.

Later author reads use `since_id` and drain all continuation pages.
An unchanged author read does not download the same ten posts again.
A newly tracked author receives historical import; a removed author receives no new timeline reads.
Stable user IDs preserve identity across handle changes.

A crash, conversion error, provider error or rejected Graph admission leaves the committed cursor unchanged.
Replaying the last page is safe.
Expired provider pagination restarts only the affected provider walk from its saved boundary.
Other completed walks and previously admitted records survive.

### Graph ownership, contacts and reads

The X module continues to own `x.profile` and `x.post`.
It additionally owns `x.direct_message`, a content entity anchored by the provider event ID.
A DM stores conversation ID, sender ID, available participant IDs, text, provider creation time and attachment references.

Use existing `authored_by` and `sent_to` relations between messages and X profiles.
Author links must resolve across page boundaries, not only within the current page.
Preserve account/user provenance and prevent another account's private conversation from appearing in reads.

Following and DM participant profiles reuse `x:profile:<user_id>`.
For each imported profile, first reuse an existing person-to-profile identity link or the explicitly tracked contact.
Otherwise derive a contact UUID from the Magnis user ID and immutable X user ID.
Call existing `contacts.create` with that UUID as `client_id`, then add the existing `identity` link.

Retrying contact creation or the identity link cannot create a second person.
Curated contact names survive synchronization.
Provider profile facts remain on the X profile.
An identity-link failure fails admission rather than disappearing behind a catch-all.

Add read-only `x.direct_messages.list` and `x.direct_messages.get` tools.
List by conversation ID with server-side filtering before pagination.
Apply the same correction to the existing `x.posts.list` author filter.
Contacts remain visible in Contacts; tracked posts remain visible in the current X feed.
A new inbox, message sending and a UI redesign are excluded.

Contacts' existing exclusion of bulk message traffic includes `x.direct_message`.
Do not copy message histories into a contact detail response.

### Progress, holds and evidence

Extend the X module's existing progress declaration with direct messages.
Count each admitted profile, post and DM once in a pass.
Bootstrap statements use pass stamps; catch-up counts only actual creates, with updates and repeats contributing zero.
Page-local duplicate remote IDs are normalized before writes and counting.
Repeated pages and property updates contribute zero new-item deltas.
Stop treating the recent-ten window as the historical target.

Do not derive an exact accessible total from an author's all-time tweet count.
State per-item plan deltas once per generation; they describe admitted work, not a known total for the unfinished walk.
Until completion, Accounts remains synchronizing; equal intermediate counts do not mean the target finished.
Enable the existing completion hook to settle counts for this account's retained X records after historical import.
That hook never sweeps records merely absent from the provider's limited history.
Provider-inaccessible history is not silently represented as downloaded.

On HTTP 429, preserve a valid Retry-After or derive remaining time from X's documented `x-rate-limit-reset`.
An absent or malformed wait is a provider error.
A credits-depleted HTTP 402 without provider retry timing is an actionable error, not an invented sixty-second hold.
After a fatal response, that page starts no further provider requests.
The host owns the durable hold and retry deadline.

Reuse `acceptance/telegram-performance` for the live report.
Its grouping already supports arbitrary Source IDs.
Add rejection of `X_FIXTURE_FILE` to its existing real-provider guard.
Retain its launcher, reset safety, persistent credential tables and saved Telegram/Google data.

Record exact app/catalog/package revisions, per-walk counts, requests, pages, replayed items, holds and fetch/admission/wall time.
An unchanged-poll report distinguishes unavoidable following enumeration from incremental post and DM reads.
Do not claim a speedup without equivalent same-account measurements.
No live Twitter or PostgreSQL execution enters CI.

## Invariants

- Step 1 → Verify: connect with valid user scopes; app-only access, missing identity, rejected tokens and malformed responses fail before any data import.
- Step 2 → Verify: expire one token during concurrent fetches; one refresh occurs, its replacement persists before data reads, and a restart uses that replacement.
- Step 3 → Verify: disconnect or repair while refresh is pending; no stale token writes into the replacement generation.
- Step 4 → Verify: import two following pages and overlapping DM participants; each provider ID produces one profile and one contact despite changed handles and page replay.
- Step 5 → Verify: interrupt a multi-page DM import; resume from the admitted cursor, preserve conversation links and store original creation times without duplicated messages.
- Step 6 → Verify: fetch new DM events over several pages; stop only at the saved boundary or provider exhaustion, and report an inaccessible gap explicitly.
- Step 7 → Verify: import 205 tracked-author posts over three pages, including long-form content; then receive twelve new posts over two forward pages without advancing early.
- Step 8 → Verify: remove one tracked author and add another; the removed author receives no timeline calls and the new author receives its accessible history.
- Step 9 → Verify: connect with zero tracked handles; following and DMs still import, while the provider receives zero author-timeline requests.
- Step 10 → Verify: fail page conversion, identity linking or Graph admission; the cursor does not advance, and successful replay preserves exact entity/contact counts.
- Step 11 → Verify: inject 429 with exact reset time, missing timing and untimed 402; only the first produces a timed hold, and no further page requests start.
- Step 12 → Verify: filter posts and messages before paging; mixed-author fixtures return a full requested page and the correct filtered total.
- Step 13 → Verify: replay progress statements and updates; neither inflates totals, and retained historical records survive provider-window expiry.
- Step 14 → Verify: certify the dependency-closed X artifact over stdio; then record one separate real-account import, unchanged poll, restart and new-item synchronization.

Each behavior starts with its scoped failing `agent:test:backend` target.
Frontend tests are required only if an approved change touches frontend behavior.
The complete `agent:verify:pr` gate runs once per PR after scoped checks.
Manual live evidence stays outside CI and contains counts rather than private messages or credentials.

## Not verified

- The owner's account type, granted scopes, endpoint entitlement and available API credit have not been inspected.
- Whether the owner needs encrypted X Chat remains unanswered; its keys and provider path must be resolved before the implementation contract.
- X may rotate refresh tokens; the restart invariant requires persisting every returned replacement rather than assuming reuse.
- Actual DM participant expansion and media access must be checked against the authorized account.
- API-bound history cannot recover ordinary DMs older than thirty days or posts outside the timeline limit.
- No real Twitter throughput, completion time, account import or UI behavior has been measured in this work.
- Account progress and Graph counts require an actual host-to-module journey; inspecting types alone does not prove either.
- Existing X connections require a reviewed reconnect path; their credentials and the saved Google/Telegram databases remain untouched during planning.
